PHASE 1

Multi-omics, end to end

The first product. Prioritise breadth, correctness, and fast pilots over any novel method. No KG yet.

Objective: a pip-installable Python package that ingests aligned multi-omics data, runs every major integration method through one interface, and evaluates them on standard tasks — validated by fast pilot studies on ready-made datasets. Benchmarks decide what's good; the package's value is breadth + reproducibility, since no single method wins across datasets.

WS 1.1 Data structures & I/O foundation

One in-memory representation everything else builds on. Get this right first — it removes friction from every later workstream.

  • Native container: MuData/AnnData (one modality per AnnData, held in a MuData), so single-cell and bulk share plumbing.
  • Loaders: MLOmics, Rappoport–Shamir benchmark, TCGA via GDC/cBioPortal, LinkedOmics, CPTAC; plus generic CSV/TSV/H5AD/MultiAssayExperiment.
  • Sample alignment: enforce a common sample index across blocks; first-class support for partial overlap (a sample missing some omics).
  • Run scaffolding: config-driven runs, deterministic seeding, run manifests for reproducibility.

WS 1.2 Preprocessing & harmonization

Most real-world effort lives here, not in the integration algorithm. Feature-ID harmonization is the hidden time sink — budget for it (and it doubles as the bridge to the KG in Phase 2).

Harmonization & missingness
  • Feature ID mapping: transcripts/probes/proteins → Ensembl / HGNC / UniProt; CpG→gene; metabolites → HMDB/ChEBI (staged for later).
  • Missing data: filtering, imputation (mean, KNN, matrix-completion, VAE modality-transfer), plus a flag to route to methods that handle missingness natively (NEMO, MOFA, CLCLSA).
Normalization, batch & selection
  • Per-omic normalization: RNA log-CPM/TPM/VST; methylation M-values; proteomics VSN/log; consistent scaling so no block dominates concatenation.
  • Batch correction: ComBat, limma, Harmony, scVI-style.
  • Feature selection / DR: variance/MAD filter, univariate association, PCA — always inside CV folds to avoid leakage.
  • QC: per-omic reports, outlier detection, distribution diagnostics.

  • ARI / NMI vs known subtypes
  • Survival separation (log-rank / Kaplan–Meier)
  • Consensus-clustering stability
Supervised

Benchmark harness (build once, reuse everywhere)
A single runner that executes every wrapped method on a dataset for a chosen task, emits comparison tables (accuracy, runtime, noise-robustness), and writes reproducible configs. This harness is what makes the pilots fast and the eventual paper credible.

WS 1.5 Pilot studies — fast, and first

Run these before the catalogue is complete, on the smallest ready datasets, to validate the plumbing and produce early results.

  • Datasets: MLOmics (fastest, ML-ready) → Rappoport–Shamir (classic clustering benchmark) → one TCGA cohort via cBioPortal (e.g. BRCA) for depth.
  • Tasks: (a) cancer subtype clustering, (b) survival stratification, (c) supervised subtype classification.
  • Output: a reproducible pilot report notebook + benchmark tables comparing all methods on accuracy, runtime, and robustness.

WS 1.6 Engineering & packaging

  • Module layout: io/ · harmonize/ · preprocess/ · integrate/ · evaluate/ · interpret/ · benchmarks/.
  • Quality floor: typed API, docstrings, tutorials/notebooks, unit tests + CI, pip packaging, docs site.
  • Compute: CPU is fine for classical methods; GPU for GNN/VAE. Document the split.

PHASE 2

The knowledge-graph layer

What the KG must contain, how it plugs into the Phase-1 pipeline, and how to prove it actually helps. The bidirectional / novel loop stays out of scope for now.

Objective: a KG module that links harmonized omics features to biological entities and feeds that structure into integration — benchmarked against the Phase-1 non-KG methods with strict ablations, so any claimed improvement is defensible.

WS 2.1 What the KG needs

Node types
  • Genes, proteins
  • Pathways, biological processes (GO)
  • Diseases, phenotypes (HPO)
  • Drugs / compounds
  • Anatomy; metabolites / lipids low coverage
Edge / relation types
  • gene–gene & protein–protein interaction
  • gene–pathway, pathway hierarchy
  • gene–disease, disease–phenotype
  • drug–target, drug–disease (indication / contraindication / off-label)

WS 2.2 Construction & the omics↔KG bridge

  • Build: ingest → normalize identifiers → dedupe/merge → confidence-score edges → store as PyG HeteroData / Neo4j / NetworkX, with provenance per edge.
  • Entity harmonization (critical): map Phase-1 harmonized feature IDs → KG node IDs; emit a per-omic coverage report (genes map well; metabolites flag gaps).

WS 2.3 Integration approaches (KG × multi-omics)

KG as feature graph

Genes/proteins are nodes, KG relations are edges, omics values are node features → run a GNN. The cleanest way to inject structure.

KG-embedding priors

RotatE / R-GCN / node2vec embeddings as node initialization or auxiliary features for the Phase-1 models.

Pathway-constrained layers

Optional biologically-informed sparse layers (P-NET style) where hidden units map to pathways for interpretability.

Patient-specific subgraphs

Extract a per-patient active subgraph from their omics rather than one fixed global graph shared by all samples.

WS 2.4 Benchmarking — prove the KG earns its place

Required ablations
Every KG claim must survive: (1) KG vs no-KG against the best Phase-1 methods (MOGONET, DeepMoIC, MOFA, SNF, DIABLO); (2) full multi-relational KG vs a single-PPI/pathway prior; (3) a random-rewire control — knowledge must beat a randomly-structured graph; (4) a leakage audit so KG-derived features can't encode the label.
  • Datasets: the same Phase-1 cancer cohorts (clean comparison) plus one low-sample setting where priors should help most (e.g. Alzheimer's).
  • Metrics: reuse the Phase-1 harness; report the lift and where it comes from.

PHASE 3

The combined package

Unify multi-omics and KG behind one interface, harden it, and ship v1.0 as a citable resource.

Objective: one package where the KG is an optional toggle on the Phase-1 pipeline, tuned for scale, fully documented, with an end-to-end example that runs raw omics → integrated model → KG-interpreted result.

WS 3.1 Unify & harden

  • One API: KG on/off as a parameter; the same evaluation harness covers both.
  • Scale: performance & memory for PrimeKG-scale graphs (~4M edges) on a single GPU; batching for large cohorts.
  • Provenance interpretation: outputs traceable to named KG entities and cited edges.

WS 3.2 Release & documentation

  • Tutorials, an end-to-end worked example, and a public benchmark leaderboard.
  • Reproducibility artifacts (versioned datasets, configs, seeds).
  • v1.0 open-source release + a methods/resource paper positioning the package as the home for these methods.
Parked for later — the novelty
The bidirectional omics ⇄ KG loop (multi-omics evidence refining KG edges) is deliberately out of scope for v1.0. It's the strongest research differentiator, but it needs careful validation; revisit it as a post-v1.0 extension once the package and KG benchmarks are solid.

Cross-cutting concerns

  • Seeds, configs, run manifests, versioned datasets

  • Every published number regenerable from a config
Compute profile
  • Classical (MOFA/SNF/DIABLO): CPU
  • GNN / VAE / single-cell: single GPU
  • KG embedding at PrimeKG scale: one modern GPU, watch memory
Team & skills
  • Bioinformatics (omics, pathways, IDs)
  • ML / GNN engineering (PyTorch, PyG)
  • Software engineering (packaging, CI, docs)
Licensing
  • Open-source throughout — not a blocker now.
  • Revisit per-method & per-dataset terms only when a paid tier is on the table.

Guiding principle throughout: breadth and correctness before novelty. Each phase produces something releasable, so value compounds even if later phases slip.

OMICS-KIT — phased work plan. Phase 1 builds the end-to-end multi-omics package (all integration methods, pre/post-processing, pilot datasets, cancer-first validation). Phase 2 adds and benchmarks the knowledge-graph layer. Phase 3 unifies both into a v1.0 open-source release. The bidirectional omics⇄KG loop is parked as a post-v1.0 research extension.
