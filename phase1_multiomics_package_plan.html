The reversed order

Package-first, not scripts-first

The earlier draft tested methods as standalone scripts and wrapped the winners afterwards. We flip it: the package scaffold is built at the start, and every method is added into it. Testing then happens on the compiled package, so what's validated is exactly what ships.

Why this is better
  • Tests validate the product. A green test means the package works, not that a loose notebook once worked.
  • No rework. Nothing is written twice — no "prototype then re-implement as a wrapper" tax.
  • Interfaces are forced early. Defining the plugin contracts up front keeps every later method honest and uniform.
  • Reproducibility is free. Because runs go through one API + config, every benchmark number regenerates from a manifest.
What it costs
  • Slower first light. No results until the skeleton exists (~Sprint 1–2). Accepted trade for zero rework.
  • Design discipline required. The plugin interfaces must be right-ish early; budget includes one refactor pass.
  • Harder to "just try" a method. Mitigated by a minimal adapter template so adding a method is low-friction.
Core principle

Disease-agnostic by construction

Cancer has the most easily available data, so the first pilots run on it — but the package must not assume it. Anything clinical-cancer-specific (Kaplan–Meier, log-rank, C-index) is a task plugin, not part of the core. A T2D or IBD study simply loads a different task with different metrics.

The rule
The core knows about omics blocks, samples, and abstract tasks. It does not know about survival, tumor subtypes, or any disease. Survival analysis (where KM/log-rank live) is registered as one optional Task among several — used only when a dataset actually has time-to-event labels.
Core (always present, domain-free)
  • Data model: N omics blocks over shared samples; partial overlap allowed.
  • Generic tasks: clustering, classification, regression.
  • Generic metrics: ARI, NMI, silhouette; F1, AUROC, AUPRC; RMSE, R².
  • Generic preprocessing: normalization, imputation, batch, feature selection, ID mapping.
Task plugins (loaded on demand)
  • Survival optional — KM curves, log-rank, C-index (cancer & other time-to-event studies).
  • Subtype label sets — dataset-specific ground truths (e.g. PAM50) live with the dataset, not the core.
  • Bio-interpretation — pathway/GO enrichment as an opt-in post-step.
  • New domains add a plugin; the core never changes.
Skeleton first

Package architecture

A registry-based plugin design: the base classes and registries are Sprint-1 work, everything else slots in behind them. This is the artifact that makes "test the compiled package" possible.

ModuleResponsibilityKey abstraction
core/Data container, registries, config, run manifests, seedingOmicsData (wraps MuData/AnnData)
io/Dataset loaders + sample alignmentDataset plugin
preprocess/Normalize, impute, batch, select, harmonize IDs, QCPreprocessor plugin
integrate/All integration methods behind one interfaceIntegrator plugin (.fit/.transform)
tasks/Task definitions + their metrics (incl. optional survival)Task + Evaluator plugin
interpret/Attribution, enrichment, visualizationInterpreter plugin
bench/Runner: any method × dataset × task → tablesBenchmark driver

Adapters bridge external ecosystems: Python packages (mofapy2, snfpy, multi-view-AE, scvi-tools) wrap directly; R packages (mixOmics, nipalsMCIA, iClusterPlus) go through one shared rpy2/reticulate bridge built once; research code (MOGONET & other GNNs) is vendored and refactored to the Integrator contract.

How estimates are set

Effort model

Effort is driven mostly by whether the method already exists as a maintained package. Wrapping a pip package is hours; reproducing research code is days.

low maintained pip/Bioc package → thin wrapper · ~5–10 h med R package or clean research code → adapter / bridge · ~7–14 h high research code to refactor & reproduce, or build · ~14–18 h

Estimates include implementation, an adapter test, a docstring, and one worked example — the real cost of putting something into a tested package, not just importing it. The first R method and the first GNN carry extra one-time infrastructure cost (the bridge, the vendoring pattern) which later methods in the same class then reuse cheaply.

The agnostic acceptance test
The IBD set has no time-to-event labels. If the package runs it end-to-end — load → preprocess → integrate → classify/regress → interpret — without touching any survival code, the disease-agnostic design is proven. That run is an explicit v0.1 acceptance criterion.

Solo @ 20 h/week — scope discipline
The plan front-loads the two one-time infrastructure costs (R bridge in Sprint 5, GNN vendor-pattern in Sprint 5) so later methods stay cheap. The biggest schedule risk is GNN reproduction — research code that doesn't run as published. Mitigation: MOGONET is the Sprint-5 spike; if it fights back, the package still ships v0.1 with four solid families and MOGONET slips to v0.2 without blocking release.
OMICS-KIT — Phase 1 build plan. Package-first: compile the skeleton, add every method as a plugin, test the compiled package. Disease-agnostic core with survival (and Kaplan–Meier) demoted to an optional task plugin. Effort sized by package availability — pip wrappers are hours, research-code reproduction is days. ~293 h to a tested v0.1 (weeks 1–15), ~157 h more to a full-catalogue v0.2 (weeks 16–24), at 20 hours per week.
